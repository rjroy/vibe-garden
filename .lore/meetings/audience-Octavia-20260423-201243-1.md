MEETING NOTES: Lore Directory Redesign Roadmap
Octavia + User | 2026-04-24

SUMMARY

Session progressed through Step 1 (distill function design) to completion and initiated Step 2 (learn dialog brainstorm). Step 1 resolved the architectural question of whether distill should be a separate skill or a mode of excavate: the decision is one skill named `/distill` with two modes (`/distill code` and `/distill build`). Reference documents function as code augmentation (capturing what code cannot express) rather than spec replacement. Distill's core operation always verifies candidate promotions against current code, with the user gatekeeping each decision. Build artifacts are classified as historical and safe to delete after distilling. Reference docs follow natural project conventions for organization; no prescriptive topology is required.

Step 2 brainstorm opened with the trigger model as the load-bearing question. Three framings were evaluated: manual invocation only (likely to underutilize the skill), automatic invocation by design-phase skills (risk of noise fatigue), and conditional offering as a follow-up when host skills surface relevant retro notes. The proposed pattern integrates `/learn` into the existing lore-researcher search flow: when `/specify` or `/prep-plan` queries lore-researcher and finds retro notes in the current module scope, the host skill offers the user a follow-up option to run `/learn` against the found notes. This honors the observation-interpretation split principle (human gates the dialog) while firing at the front of new work (when design-phase skills run).

KEY DECISIONS

Step 1 (Distill Function):
- Single skill `/distill`, renamed from `/excavate`, with two modes
- Reference augments code, does not replace specs
- Distill always verifies against code before promoting; AI proposes, user decides placement
- Output fan-out is variable (unconstrained by mode)
- Null output (no promotions) is valid and requires no justification
- Build artifacts treated as historical; distill-then-delete is the clean path

Step 2 (Learn Dialog):
- Trigger model: `/learn` offered conditionally by host skills (not manual-only, not automatic)
- Integration point: lore-researcher search results in `/specify` and `/prep-plan` surface retro notes, triggering the offer
- Reuses existing tag/module/title search infrastructure for relevance ranking
- Principle 3 (observation-interpretation split) enforced structurally: user must explicitly accept the offer
