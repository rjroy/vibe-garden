# Spec: Spec Review What vs How Separation

## Overview

Update `lore-docs-reviewer` (renaming to `spec-reviewer`) and `specify` skill to prevent specs from drifting into implementation territory. The core insight: specs should answer "what are we building and how will we verify it's done?" not "how do we build it?" The reviewer currently invites implementation thinking by asking "Could I implement this?" which causes premature specification that undermines progressive discovery.

**Progressive discovery** means building and discovering context a piece at a time so that each piece matters and fits into place. If you try to do it all at once, you leave gaps. These gaps, while making things go fast, are where the appearance of completeness demonstrates its failures. This is akin to Anthropic's "progressive disclosure" in the skills system. Premature "how" specification short-circuits this process by anchoring the AI on implementation details before the full picture emerges.

## Entry Points

- User invokes `spec-reviewer` agent on a spec (via Task tool or after `/specify`)
- User runs `/specify` to create a new spec

## Requirements

### Two Types of "How"

- REQ-1: Both files must distinguish between "how to verify" (belongs in spec) and "how to build" (belongs in plan)
  - Example of "how to verify": "User can authenticate and access protected resources"
  - Example of "how to build": "Use JWT tokens with RS256 algorithm, store refresh tokens in httpOnly cookies"
- REQ-2: The distinction must be stated explicitly, not just implied by question framing

### Rename and Refocus

- REQ-3: Rename `lore-docs-reviewer` to `spec-reviewer` (file rename: `lore-docs-reviewer.md` → `spec-reviewer.md`)
- REQ-4: Update agent description to reflect spec-only focus
- REQ-5: Remove references to reviewing plans. Plans are generated by native PlanMode and cannot be reviewed by this system.

### spec-reviewer Lens Changes

- REQ-6: Rename Lens 4 from "Actionability" to "Verifiability"
- REQ-7: Reframe Lens 4 questions from "Could I implement this?" to "Could I verify this was done?"
- REQ-8: Add explicit "What vs How" guidance in the Behavior Guidelines section

### specify/SKILL.md Changes

- REQ-9: Update reference from `lore-docs-reviewer` to `spec-reviewer` in the fresh-eyes review section
- REQ-10: Add explicit "What vs How" boundary statement near "Keep It Light" section
- REQ-11: Include anti-patterns that signal crossing into plan territory (e.g., specifying algorithms, file structures, implementation steps)
- REQ-12: Clarify that "how to verify" belongs in spec, "how to build" does not

## AI Validation

**Defaults apply.**

**Custom:**
- After implementation, run the updated reviewer on an existing spec and confirm feedback focuses on verification, not implementation

## Constraints

- Changes must not break the existing Entry/Exit Points model or stub notation
- The "Keep It Light" philosophy must be preserved, not weakened
- Both files must use consistent terminology for the what/how distinction
- Terminology consistency matters: use "plan" (noun, the artifact from PlanMode) not "planning" (verb/process) when referring to where implementation details belong. Consistency, even if boring, prevents confusion.
